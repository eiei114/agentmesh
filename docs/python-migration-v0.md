# Python port conventions v0

The Python controllers that run the owner's Multica operation (the vault's
`4_Project/Multica-Agent-Strategy/Scripts/`) move into this repo as ops crates.
AI writes each port, its tests and the shadow comparison. Python stays the
authority; switching a controller to the Rust build is the owner's decision,
made from shadow evidence. Status: unstable.

## Crate layout

One Python module, or one function group of a large module (about 150-500
lines of logic), becomes one crate:

```text
plugins/ops/<module-kebab>/
  Cargo.toml        # package agentmesh-ops-<module-kebab>, publish = false, [lints] workspace = true
  src/lib.rs        # the deterministic core: parse, evaluate, select, classify, decide
  src/main.rs       # stdio binary: agentmesh_ops_kit::run_stdio(<handler>)
  testdata/
    README.md       # the exact command that produced the expected files
    <case>.input.json
    <case>.expected.json
  tests/parity.rs   # agentmesh_ops_kit::check_parity over testdata/
```

- The `plugins/ops/*` member glob in the root `Cargo.toml` picks the crate up;
  do not edit the root `Cargo.toml`.
- Depend on the shared kit by path: `agentmesh-ops-kit = { path = "../kit" }`.
  Use workspace dependencies (`serde.workspace = true`, ...) for anything the
  root already declares. A new third-party dependency is a serial change.
- Port the deterministic core only. Multica CLI calls, git, file writes and
  network access stay out of the crate or behind a trait the tests fake. Live
  Multica mutation is never part of a port.
- Do not depend on `agentmesh-host` or `agentmesh-conformance`.

## Stdio JSON shape

The binary reads one JSON document from stdin and writes one JSON document and
a newline to stdout (`agentmesh_ops_kit::run_stdio`).

| Outcome | stdout | exit |
|---|---|---|
| success | the handler's result, the same JSON the Python function returns | 0 |
| request is not JSON, or does not match the input shape | `{"error": {"kind": "invalid_request", "message": "..."}}` | 2 |
| handling a valid request failed | `{"error": {"kind": "failed", "message": "..."}}` | 1 |

The request carries everything the Python function reads: its arguments and
the file or CLI data it would have loaded, already loaded by the vault wrapper.
Keep field names identical to the Python dict keys so the shadow comparison is
a plain JSON comparison. Messages must not contain secrets or absolute paths.

## Parity fixtures

- `testdata/<case>.input.json` is the request; `testdata/<case>.expected.json`
  is the Python output for it (or the error document above).
- Inputs are synthetic or recorded with secrets, real issue IDs and vault paths
  removed. Plugin testdata may use synthetic Multica-shaped JSON only.
- Expected files are generated by running the Python implementation from the
  vault checkout, never written by hand. Put the exact command in
  `testdata/README.md`. Reuse the cases of the module's Python tests.
- `check_parity` compares JSON values: key order and whitespace do not matter,
  but `1` and `1.0` differ, so emit floats where Python emits floats. Every
  input needs an expected file and the reverse; an empty `testdata/` fails.

## Checks

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

## Parallel PRs

Up to four port PRs run at once. A port PR changes files only under its own
`plugins/ops/<crate>/` plus its own package entries in `Cargo.lock`. A
`Cargo.lock` conflict is resolved by rebasing on `main` and running
`cargo check --workspace`, never by hand. Root `Cargo.toml`, `deny.toml`, CI
workflows, `AGENTS.md`, `docs/`, `plugins/ops/kit` and any crate another open PR
touches are serial changes.

## After merge

The vault pins the binary through its root `mise.toml` by commit and runs it in
shadow next to Python, recording mismatches. Cutover is a separate owner
decision per controller.
